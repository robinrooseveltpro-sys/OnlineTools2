    An XML sitemap gives search engines a structured list of URLs that a website wants to make available for crawling. A sitemap can help search engines discover important pages, especially on large websites, new websites, or sites with complex internal navigation. A sitemap does not guarantee that its URLs will be crawled or indexed, but a correctly formed file makes the submitted URL list easier to process.

    1. What is an XML sitemap?

    An XML sitemap is a structured document that lists URLs associated with a website. Its most common form uses a root element named urlset and individual url entries. Each URL entry normally contains a loc element identifying the page. An optional lastmod element can describe when that page was last significantly modified.

    Search engines can use sitemap information as a discovery signal. It can be helpful when a website has many pages, recently published pages, pages that are not linked prominently from the homepage, or a structure that makes URL discovery more difficult. Internal links and other discovery methods still matter: a sitemap is not a substitute for a crawlable website architecture.

    A sitemap typically lists the canonical URLs that a site wants search engines to consider. Avoid intentionally listing URLs that redirect to another destination, duplicate pages that should consolidate elsewhere, error pages, or URLs that are not meant to appear in search results. Keep the list consistent with the website's actual URL structure.

    An XML sitemap is different from an HTML sitemap. An HTML sitemap is a page primarily intended to help visitors navigate a site, while an XML sitemap follows a format intended for search-engine discovery. A site can use both when each serves a useful purpose.

    2. What does an XML sitemap validator check?

    A sitemap validator examines whether the supplied XML can be parsed and whether its main elements follow the expected sitemap structure. This helps identify problems such as unclosed tags, mismatched elements, missing location values, and root elements that do not represent a normal URL sitemap or a sitemap index.

    It can also inspect the contents of each entry. A URL should be an absolute address rather than a relative path, and optional date information should be formatted correctly. Duplicate locations can indicate unnecessary repetition, while an incorrect namespace can prevent a file from conforming to the expected sitemap format.

    This tool reports structural errors separately from advisory issues. A missing optional lastmod value, for example, is not the same type of problem as malformed XML. A valid-looking XML document can still contain unsuitable URLs, incorrect dates, or outdated page addresses, so the results should be reviewed in context.

    Local validation does not establish that a web server returns a successful response for every listed page. It also cannot determine whether a page is blocked by a robots rule, declares a different canonical URL, or is eligible for indexing. Those questions require separate website and search-console checks.

    After a corrected sitemap has been uploaded to your website, check the public file at its actual URL. Then submit or resubmit the sitemap address through the relevant webmaster tools if appropriate. Search engines may need time to fetch and process the update.

    4. XML syntax errors and common sitemap problems

    XML requires properly nested and closed elements. For example, an opening url element must have a matching closing tag, and a child element must be closed before its parent ends. A mismatched closing tag, unescaped ampersand, or truncated file can prevent a parser from reading the document.

    Attribute values and text must also follow XML rules. A raw ampersand used as part of a URL query should normally be encoded as &amp; in the XML source. When the XML is parsed, the entity is decoded back to the ampersand that belongs in the URL. This distinction is important when a sitemap lists URLs with query parameters.

    Another frequent issue is the wrong root structure. A conventional URL sitemap uses urlset, while a sitemap index uses sitemapindex. Mixing their child element types can make the document structurally incorrect even if the XML syntax itself is valid.

    Use a validator to locate the problem, then correct the file at its source. If a content-management system generates the sitemap automatically, fix the relevant configuration or page data rather than repeatedly editing a generated file that will be overwritten.

    5. What are urlset and sitemap index files?

    A urlset sitemap lists individual webpage locations. Each url element represents a location, with optional metadata such as last modification time. It is the familiar format used by websites that have a manageable number of sitemap entries in one file.

    A sitemap index contains references to other sitemap files. Its root element is sitemapindex, and its child entries are sitemap elements. Each entry normally contains a loc value pointing to a child sitemap. The index makes it possible to organise a larger URL inventory into multiple files.

    The distinction matters during validation. A normal URL sitemap contains page locations, whereas an index points to sitemap documents. A sitemap index should not be treated as though each of its child locations were a webpage entry in a regular sitemap.

    When validating an index, check that every child sitemap location is absolute and that the referenced sitemap files are published and accessible. This browser-based validator checks the structure and addresses listed in the index, but it does not recursively download and validate each child sitemap.

    6. What is the sitemap XML namespace?

    A standard sitemap declares the namespace http://www.sitemaps.org/schemas/sitemap/0.9 on its urlset or sitemapindex root element. The namespace identifies the vocabulary used by the document and helps XML-aware software distinguish sitemap elements from unrelated XML elements.

    A common sitemap declaration looks like this:

    <urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">

    A document can be well-formed XML without using the correct sitemap namespace. For that reason, parsing successfully is only the first step. A validator should also check whether the root structure uses the expected sitemap vocabulary and whether location entries are in the appropriate place.

    Some sitemap files include extension namespaces for images, video, news, or language-related annotations. Such extensions can add useful metadata, but they do not remove the need for the standard sitemap structure. The validator focuses on common URL and sitemap-index requirements rather than fully validating every extension schema.

    7. What is lastmod in a sitemap?

    The lastmod element describes the date or date-time when a page was last significantly modified. It can provide useful information about changes that matter to search engines. A significant change can include a meaningful update to the main content, structured data, or important links.

    A simple value can use the ISO-style date format 2026-10-19. A date-time value may include the time and time-zone information. The exact value should reflect the actual modification rather than a date invented solely to make a sitemap appear new.

    Missing lastmod is not automatically a fatal structural error. However, incorrect or misleading dates should be corrected. The presence of the element is useful only when its information is reasonably accurate. Updating every page's lastmod each time an unrelated file changes can reduce the value of the metadata.

    This validator checks the syntax of supplied lastmod values and reports their coverage. It cannot independently confirm when the corresponding webpage was actually updated. Compare the dates with your website's publishing process or source-control history when accuracy matters.

    8. How many URLs can an XML sitemap contain?

    Google's published sitemap guidance specifies a maximum of 50,000 URLs or 50 MB uncompressed for a single sitemap file. A sitemap that exceeds those limits should be split into smaller sitemaps, with a sitemap index used when appropriate. See Google's sitemap-index documentation.

    These limits apply to the sitemap format accepted by Google; other crawler implementations may provide additional guidance. This tool uses the commonly documented Google limits as a practical validation baseline rather than claiming that every search engine has identical processing rules.

    A website with fewer than the maximum number of pages can still benefit from multiple files when the content has clear sections, languages, page types, or separate publishing systems. Dividing a sitemap can make management and debugging easier even before a file reaches the technical size limit.

    Count and size are different measurements. A sitemap containing a modest number of very long URLs may consume more space than expected, while a compact sitemap with short URLs can contain many entries. Always review both metrics when diagnosing a large-sitemap problem.

    9. What makes a sitemap URL valid?

    A sitemap location should be a complete absolute URL, including its scheme and hostname. For example, https://example.com/about.html identifies a complete address. A relative path such as /about.html is not an equivalent replacement for the absolute location in a sitemap.

    Check that URLs use the intended hostname, scheme, and canonical version of the website. If your site redirects HTTP pages to HTTPS, the sitemap should generally list the canonical HTTPS addresses instead of repeatedly listing the redirecting alternatives. The same principle applies to unwanted hostname, slash, or file-extension variations.

    An absolute URL can still be an unsuitable sitemap entry. The page may return an error, be redirected, be blocked from crawling, or specify another canonical URL. Structural validation checks address formatting; it does not establish that the destination is eligible for indexing.

    Sitemap URL choices should match the site's actual publishing configuration. Make sure the locations listed in the sitemap are reachable, canonical, and intended to be discovered through search engines.

    10. Why duplicate URLs and redirects matter

    Duplicate entries list the same location more than once in a sitemap. Repetition usually provides no additional discovery value and can indicate an export or generation problem. Remove duplicates so that the sitemap remains clear and easier to inspect.

    Redirecting URLs can also make a sitemap less useful. If an old page redirects to a current canonical page, update the sitemap to list the final URL where appropriate. Maintaining obsolete locations can make the file harder to manage and does not replace proper redirect handling.

    A duplicate URL is not the same thing as duplicate webpage content. Two different addresses might display similar content even though both addresses are unique strings. A sitemap validator can identify repeated locations in the XML, but content duplication and canonicalisation require additional checks.

    After updating the file, inspect important pages individually in Google Search Console or another crawler when necessary. Confirm that the intended canonical URL responds correctly and that internal links point to the version you want search engines to discover.

    11. How to submit a sitemap to Google and Bing

    After publishing a valid sitemap at a public URL, add or submit that URL through the relevant webmaster service. Google Search Console provides a Sitemaps section for submitting and reviewing known sitemaps. Bing Webmaster Tools provides sitemap submission and reporting features for verified sites.

    You can also declare a sitemap location in the site's robots.txt file using a Sitemap directive. The URL should be absolute, for example: Sitemap: https://example.com/sitemap.xml. This helps crawlers discover the file, but it does not guarantee that they will crawl every listed page.

    Submit the public sitemap location, not the contents of the XML pasted into this validator. The validator only checks the supplied text in the browser. Your actual sitemap must be hosted at a reachable URL that the search engine can fetch.

    After submission, review the webmaster service's status and any reported fetch or parsing errors. Correct the source sitemap or hosting issue when a failure is reported. A successful submission means the file has been provided for processing; it does not mean that every page will be indexed.

    12. Can this validator test a sitemap URL directly?

    Yes, it can attempt to retrieve a sitemap from a URL you enter. When the sitemap is available from the same website or the remote server permits cross-origin access, the validator can read the response and inspect its XML.

    Browsers enforce cross-origin restrictions. A third-party sitemap server may refuse to expose its response to this page even though you can open that sitemap directly in a browser tab. This is a browser security policy, not proof that the XML is invalid. The MDN CORS documentation explains this restriction.

    When remote fetching is blocked, download the sitemap through your browser and upload its XML file into the validator, or copy and paste the contents. Local validation remains useful for syntax and structure even when direct retrieval cannot be completed from this page.

    The direct-fetch feature does not behave like a server-side crawler. It does not impersonate Googlebot or Bingbot, recursively fetch sitemap index children, or independently verify all listed webpage response codes.

    13. What are changefreq and priority?

    Older sitemap examples often include changefreq and priority. The first describes an expected update frequency such as daily or weekly. The second expresses a relative priority within the website's URL list. Both are optional sitemap metadata.

    Google documents that it ignores the priority and changefreq values. Adding them therefore does not compel Google to crawl a page more often or to rank it above another page. An accurate lastmod value is a more useful signal when it genuinely reflects a significant update.

    You do not need to add these optional values to every sitemap merely because an example contains them. Focus on valid locations, a correct XML structure, accurate modification dates where supplied, and a sitemap file that matches your current canonical URLs.

    14. Common XML sitemap validation errors

    XML parsing error

    Check for missing closing tags, mismatched elements, invalid entities, truncated XML, and malformed attributes. Correct the XML source before submission.

    Missing loc element

    Each sitemap URL entry and each sitemap-index entry needs an appropriate location element. Check the XML element structure and ensure that the location has a meaningful value.

    Relative URL instead of an absolute URL

    Replace relative paths with complete addresses that include the scheme and hostname. Use the intended canonical URL rather than a shortened path.

    Invalid lastmod value

    Use an appropriate date or date-time format and ensure the value represents an actual page update. Avoid placeholder strings or invented dates.

    Duplicate URL entries

    Remove repeated locations and review the sitemap generator if the duplicates return after publishing a regenerated file.

    Too many URLs or excessive file size

    Split the sitemap into smaller files and use an index when appropriate. Check both uncompressed file size and entry count before publishing.

    15. Frequently asked questions about sitemap validation

    Is this XML sitemap validator free?

    Yes. You can paste XML or upload a supported file and run the validator in your browser without creating an account.

    Can it validate a sitemap index?

    Yes. It recognizes the standard sitemap-index structure and checks its sitemap entries and required location values. It does not recursively download and validate each child sitemap.

    Does a valid sitemap guarantee indexing?

    No. Sitemap validity means the file passes the checks performed by this tool. Indexing also depends on crawling, canonicalisation, content, access rules, and the search engine's systems.

    How many URLs can a sitemap contain?

    Google's published guideline allows up to 50,000 URLs in one sitemap and a maximum uncompressed size of 50 MB. Larger URL sets can be split into separate sitemap files.

    Does the tool support compressed .gz sitemaps?

    This browser-only version accepts uncompressed XML text, not gzip-compressed sitemap files. Extract the XML before uploading it.

    Can it check whether each URL returns HTTP 200?

    No. It checks URL formatting and sitemap structure. Live status checks require separate requests to the target pages and may be restricted by browser security policies.

    Why does fetching a public URL sometimes fail?

    The remote server may block browser cross-origin access, the URL may be unavailable, or the server may return an error. Try downloading the XML and uploading the local file instead.

    Is lastmod required?

    It is optional in standard sitemap entries. When supplied, it should accurately reflect the page's significant modification date.

    Do priority and changefreq improve rankings?

    Google says it ignores these values. Prioritise accurate sitemap locations and lastmod information instead of relying on optional hints.

    Can I use this for Bing Webmaster Tools?

    Yes. XML structure and common sitemap checks are useful before submitting the file to Bing or another search engine. Consult each service's guidance for additional requirements.

    Does the validator change my sitemap file?

    No. It validates the supplied XML and provides diagnostics. Correct the source file separately and validate the updated version.

    Can a sitemap contain HTML pages and tool URLs?

    A sitemap can list canonical URLs for pages you want search engines to discover, including tool pages. Ensure those addresses are absolute, reachable, and intended for indexing.
